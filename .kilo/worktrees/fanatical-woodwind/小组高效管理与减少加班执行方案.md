## 一、团队原则

向团队统一说明核心理念：

> 我们不鼓励长期加班，团队按结果交付。
> 当天任务完成、质量达标、不影响协作，可以早点走。
> 如果任务做不完，必须提前反馈，不能等到下班才说。

好领导的关键不是让大家少干活，而是让大家高效干活：

- 任务分配清楚，工作量评估合理；
- 过程及时跟进，问题提前暴露；
- 高效员工不吃亏，低效问题不放任；
- 项目压力不简单转嫁给组员。

最终目标不是"没人加班"，而是：**让加班变成偶发情况，而不是团队常态。**

可以直接对团队这样说：

> 最近项目节点比较紧，我不希望大家长期靠加班推进。
> 接下来我们按结果交付：当天任务完成、质量达标、不影响协作，就可以早点走。
> 但如果任务做不完，必须提前反馈，不能拖到下班才说。
> 我会尽量把任务拆清楚，也希望大家主动暴露问题。
> 我们的目标是提升效率，而不是靠加班硬扛。

## 二、每日管理

### 2.1 任务布置（上午同步）

每天上午花 10 分钟同步，每个任务下发时必须明确：

1. **做什么**：任务内容；
2. **何时完成**：截止时间；
3. **做到什么程度算完成**：验收标准；
4. **卡住多久要反馈**：反馈规则。

示例：

> 今天下班前完成 A 模块联调，要求代码提交、基础测试通过、问题记录清楚。
> 如果卡住超过 1 小时，必须及时反馈。

**为什么让组员参与时间预估：**

组长经验丰富、效率高，容易低估任务难度。对组长来说简单的事情，对组员可能需要更长时间。

让组员参与预估，可以帮助组长判断：

- 任务是否被低估；
- 组员是否理解任务；
- 哪些地方存在不确定性；
- 哪些人需要支持或培养。

这样任务安排会更公平，也更接近实际。

---

### 2.2 下午 3 点风险检查

统一确认一句话：

> 今天的任务能不能按时完成？

如果不能，马上判断原因并处理：

| 原因         | 处理方式                   |
| ------------ | -------------------------- |
| 任务估错     | 调整任务量或截止时间       |
| 需求不清     | 组长补充目标和验收标准     |
| 外部阻塞     | 组长协调资源               |
| 能力不足     | 拆小任务、给方法、安排辅导 |
| 拖延或不反馈 | 明确提醒，要求后续及时同步 |

**为什么设置 3 点检查：**

很多加班不是因为任务真的太多，而是因为问题暴露太晚。如果下班前才发现任务做不完，就只能靠加班补救。

下午 3 点检查可以提前发现风险：

- 能调整任务优先级；
- 能及时协调资源；
- 能决定是否延期；
- 能避免无效加班。

---

### 2.3 下班规则

满足以下条件，可以下班：

- 当天任务已完成；
- 交付质量达标；
- 测试、文档、交接已完成；
- 不影响其他同事继续工作；
- 遗留问题已说明。

同时要明确：

> 不因为某个人做得快，就无限追加任务。
> 否则高效的人会觉得自己吃亏。

**为什么允许提前完成的人早走：**

如果员工高效完成任务，却还要留下来"装忙"，会形成低效文化。谁做得快就给谁无限加活，高效员工会觉得不公平。

允许提前完成、质量达标的人早点走，可以传递一个信号：团队奖励效率，而不是奖励耗时间，有利于提升积极性和责任感。

**为什么不能纵容长期低效：**

不鼓励加班，不等于没有要求。如果任务合理、标准清楚、过程也有反馈机制，但某个人长期做不完，就需要管理介入：

- 拆小任务；
- 给模板和方法；
- 安排辅导；
- 明确能力提升目标；
- 对不主动反馈或拖延行为进行提醒。

团队要有温度，但也要有边界。

---

## 三、异常处理

任务没有完成时，不要立刻判断为个人问题，而是按以下顺序复盘：

1. 任务量是否合理？
2. 目标和验收标准是否清楚？
3. 是否存在外部依赖或阻塞？
4. 组员能力是否匹配？
5. 过程中是否及时反馈？
6. 是否存在拖延或责任心问题？

根据原因采取对应措施。

**为什么不能简单说"做不完就自己加班"：**

这句话虽然强调结果，但容易让组员感觉领导在甩责任。因为任务做不完，可能有多种原因：

- 任务本身安排过多；
- 需求没有讲清楚；
- 外部依赖没有解决；
- 组员能力还不够；
- 执行过程中遇到未知问题；
- 个人效率或主动性确实不足。

如果不区分原因，直接归结为个人问题，会削弱团队信任。

## 四、每周复盘

每周花 20 分钟复盘三件事：

1. 哪些任务预估不准？
2. 谁经常卡住，原因是什么？
3. 下周任务怎么分更合理？

可使用简单记录表：

| 成员 | 任务     | 预估时间 | 实际时间 | 偏差原因   | 后续措施       |
| ---- | -------- | -------: | -------: | ---------- | -------------- |
| A    | 模块联调 |     1 天 |   1.5 天 | 接口不稳定 | 提前确认接口   |
| B    | 测试脚本 |   0.5 天 |   0.5 天 | 正常       | 保持           |
| C    | 功能开发 |     1 天 |     2 天 | 代码不熟   | 拆小任务并辅导 |
|      |          |          |          |            |                |

连续执行两到三周后，可以判断：

- 工作量是否合理；
- 谁效率高；
- 谁需要辅导；
- 哪些流程影响效率。
